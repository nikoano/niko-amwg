# niko-amwg

Свой VPN-сервер **AmneziaWG 3.1** на голой убунте: одна команда установки, дальше
клиенты добавляются утилитой `amwg` — из меню или флагами. Без докера, без
веб-панели, без официального клиента Amnezia с его деплоем по ssh.

- обфускация поколения **3.1** целиком: защита заголовков, паддинг контента,
  плавающие тайминги, случайные хвосты — то, чего нет ни в одной панели;
- клиент заводится одной командой и уезжает в телефон qr-кодом;
- видно, кто когда подключался и сколько скачал;
- **переживает обновление ядра** — модуль пересобирается и грузится сам.

```
install.sh   установка сервера
amwg.py      утилита управления клиентами (ложится как /usr/local/bin/amwg)
debs/        официальные пакеты AmneziaWG 3.1, снятые про запас (~1 МБ)
```

## Что нужно от сервера

По умолчанию ставится ядерный модуль, поэтому у машины должно быть **своё
ядро**: KVM-виртуалка или железо. Нужен и пакет заголовков к нему — без
`/lib/modules/$(uname -r)/build` dkms нечем собирать (см.
[Если что-то не работает](#если-что-то-не-работает)).

На OpenVZ/LXC-«VPS» модуль не загрузить вовсе: там ядро общее с хостом. Для таких
машин и для ядер без заголовков есть `--userspace` — см.
[Ядро или userspace](#ядро-или-userspace); ему нужен только `/dev/net/tun`.

Ubuntu 24.04 или 22.04 — самый гладкий путь, debian и прочие apt-дистрибутивы
тоже поддержаны.

## Установка

```sh
curl -fsSL https://raw.githubusercontent.com/nikoano/niko-amwg/master/install.sh | bash -s -- --endpoint vpn.example.com
```

Всё, что нужно передать, — адрес, по которому клиенты будут приходить. Не передашь
— в живой консоли скрипт один раз спросит (предложив найденный внешний ip), а без
консоли молча возьмёт его же. Домен лучше ip: сменишь сервер — переставишь
A-запись, и старые конфиги останутся рабочими. Остальное имеет разумные умолчания: интерфейс
`awg0`, подсеть `10.9.9.0/24`, порт `443/udp`, DNS `1.1.1.1`, MTU `1280`.

Скрипт неинтерактивный: через пайп спрашивать нечего. В конце он заводит первого
клиента (`client1`) и печатает его конфиг и qr — телефон подключается сразу.

Нужна не убунта, свой порт, своя подсеть — см. [Установка подробно](#установка-подробно).

## Повседневное: `amwg`

Без аргументов — меню: стрелки, **цифры** (набирается и многозначный номер),
пробел — отметить несколько, Enter — подтвердить, `q` — назад.

```sh
amwg                        # меню
amwg add phone --qr         # новый клиент, qr сразу в терминал
amwg list -v                # кто есть, когда подключался, сколько скачал
amwg show phone --png ~/phone.png
amwg disable phone          # снять с сервера, ключи сохранить
amwg rm phone --yes
amwg stats --watch          # живой трафик по клиентам
amwg check                  # всё ли живо
amwg backup                 # один json со всем сервером
```

| Команда | Что делает |
|---|---|
| `amwg list [-v] [--json]` | клиенты: ip, статус, последний хендшейк, трафик |
| `amwg add <имя> [--qr] [--note …] [--ip …]` | новый клиент + печать конфига |
| `amwg show <имя> [--qr] [--png ф] [--out ф]` | отдать конфиг: текстом, qr, картинкой, файлом |
| `amwg disable <имя>…` / `enable <имя>…` | выключить/включить, не теряя ключи |
| `amwg rm <имя>… [--yes]` | удалить насовсем |
| `amwg stats [<имя>] [--watch] [--json]` | трафик и последнее подключение |
| `amwg server [--endpoint …] [--dns …] [--mtu N]` | параметры сервера; с флагами — правка |
| `amwg apply` | перегенерить `[Peer]` и синкнуть на живой интерфейс |
| `amwg poll` | сложить счётчики в `traffic.json` (делает таймер) |
| `amwg check` | диагностика: модуль, юниты, форвардинг, NAT, порт, пиры |
| `amwg validate [файл]` | ест ли установленная версия этот конфиг |
| `amwg backup [файл]` | весь сервер одним json (ключи внутри) |
| `amwg restore <файл>` | раскатать его здесь |
| `amwg up` / `down` / `restart` | интерфейс через systemctl |

Изменения применяются через `awg syncconf` — **без рестарта интерфейса**: чужие
сессии не рвутся, добавление и удаление клиента для остальных незаметно.

### Что стоит знать про эти команды

- **Выключение** — это снятие пира с интерфейса при сохранении ключей и адреса.
  Для ядра «выключен» и «нет такого» неотличимы; `enable` возвращает как было.
- **Трафик** ядро считает от последнего подъёма интерфейса, а пир, которого сняли
  и вернули, начинает с нуля. «Всего за всё время» поэтому складывается снаружи —
  таймером `amwg-poll.timer` раз в 5 минут. Отсюда две оговорки: до 5 минут
  трафика теряется при внезапном падении, и вся история живёт в `traffic.json`.
  В колонках «принято/отдано» — текущая сессия, в `-v` — накопленное.
- **Последнее подключение** переживает рестарты: запоминается максимальный
  хендшейк и последний адрес клиента, даже если интерфейс потом лежал.
- **«Онлайн»** — хендшейк моложе трёх минут на поднятом интерфейсе.
- **qr** — это `qrencode` по готовому конфигу. Конфиг с полным набором 3.1 весит
  ~800 байт, и qr выходит примерно 48 строк на **99 колонок**: в стандартное окно
  на 80 колонок он не влезает, переносится и после этого не читается ничем.
  Утилита ширину меряет и говорит прямо — разверни окно, уменьши шрифт или
  сохрани картинкой: `amwg show <имя> --png ~/phone.png`.
- **Имя клиента** на сервере — до 31 символа, буквы (в том числе русские), цифры,
  точка, подчёркивание, дефис. А вот **мобильные приложения имя туннеля режут
  жёстче**: и вайргардовское, и форк Amnezia требуют `[a-zA-Z0-9_=+.-]` и не
  длиннее 15 символов (`NAME_MAX_LENGTH = 15` в их исходниках). Такое имя при
  импорте телефон просто не примет и попросит другое — связь «клиент в списке ↔
  туннель в телефоне» при этом теряется. Утилита про это предупреждает при `add`,
  но не запрещает: на сервере имя остаётся как есть.
- **Приватные ключи клиентов лежат на сервере** (`state.json`, 0600). Иначе
  «покажи конфиг ещё раз» невозможно. Кому так не годится:
  `amwg add <имя> --pubkey <ключ>` — пару генерит клиент, сервер знает только
  публичную часть, а параметры для ручной сборки конфига берутся из `amwg server`.

## Клиенты

Поколение 3.1 понимают только официальные приложения Amnezia:

| Платформа | Что ставить |
|---|---|
| Windows | `amnezia-vpn/amneziawg-windows-client`, релиз 3.1.0+ (есть standalone MSI) |
| Android | `amnezia-vpn/amneziawg-android` |
| iOS/macOS | `amnezia-vpn/amneziawg-apple` |
| Linux | `awg-quick` из тех же `amneziawg-tools` |

Сторонний WG Tunnel и прочие «поддерживаем AmneziaWG» — это поколение 1.5, конфиг
отсюда они не возьмут.

## Эксплуатация

### Юниты

Своих юнитов три, плюс штатный от Amnezia. Установщик включает их сам, руками
ничего делать не нужно:

| Юнит | Чей | Что делает | В автозапуске |
|---|---|---|---|
| `awg-quick@awg0.service` | из пакета `amneziawg-tools` | поднимает интерфейс по `awg0.conf` | да, `enable` |
| `awg-quick@awg0.service.d/10-amwg.conf` | наш дроп-ин | `Restart=on-failure`, пять попыток по 30 с | — |
| `amwg-ensure-module.service` | наш | собрать и загрузить модуль до подъёма интерфейса | да, `enable` |
| `amwg-poll.timer` | наш | раз в 5 минут копит трафик клиентов | да, `enable` |
| `amwg-poll.service` | наш | сама разовая работа для таймера | нет, дёргается таймером |

```sh
systemctl status awg-quick@awg0 amwg-ensure-module
systemctl list-timers amwg-poll.timer
amwg check                 # то же самое и ещё десяток проверок разом
```

### Ядро или userspace

По умолчанию — ядерный модуль: он шифрует и форвардит, не выходя из ядра, и это
заметно дешевле по процессору. Флаг `--userspace` ставит вместо него
`amneziawg-go` — ту же реализацию протокола, но обычным процессом с
tun-интерфейсом (именно на ней работает официальный docker-образ Amnezia).

| | ядро (по умолчанию) | `--userspace` |
|---|---|---|
| скорость | быстрее, крипта и форвардинг в ядре | медленнее, каждый пакет ходит через процесс |
| зависимость от ядра | нужны заголовки и dkms, пересборка после обновления | никакой, нужен только `/dev/net/tun` |
| откуда берётся | пакеты из PPA | собирается из исходников (готовых бинарей у Amnezia нет) |
| работает на OpenVZ/LXC | нет | да, если провайдер дал tun |
| падение процесса | нечему падать | процесс никто не перезапустит автоматически |

Что меняется в установке: ставится только `amneziawg-tools` (метапакет с dkms не
нужен), собирается `amneziawg-go` в `/usr/local/bin` (сборка занимает секунды и
тянет только компилятор), в дроп-ин юнита добавляется
`Environment=WG_QUICK_USERSPACE_IMPLEMENTATION=amneziawg-go`, а
`amwg-ensure-module` не ставится вовсе — пересобирать под новое ядро нечего.

**Утилите ничего говорить не нужно**: `amwg` определяет бэкенд сам, по факту
(есть `/sys/module/amneziawg` — ядро, иначе бинарь `amneziawg-go`). Всё остальное
для неё одинаково: `awg show`, `syncconf` и `setconf` ходят и в netlink, и в
unix-сокет go-реализации прозрачно, так что клиенты, трафик, бэкапы и qr работают
ровно так же. `amwg check` и `amwg validate` подстраиваются: в userspace они не
ищут dkms и заголовки, а временный интерфейс для проверки поднимают через
`amneziawg-go`.

Конфиги клиентов при смене бэкенда **не меняются** — на проводе это один и тот же
протокол 3.1. Переехать можно и потом: снести (`install.sh --uninstall --yes`,
ключи он сложит в `/root`), поставить заново с флагом и раскатать бэкап.

Единственная неприятность userspace: если go-процесс умрёт, systemd этого не
заметит — `awg-quick@` это oneshot, он лишь запускает процесс. `amwg check`
покажет пропавший интерфейс, но автоматического перезапуска нет.

### Проверки: `check` и `validate`

| Команда | Когда запускать | Что делает |
|---|---|---|
| `amwg check` | после установки, после любого обновления, когда «что-то не работает», можно в мониторинг | полтора десятка проверок разом: модуль, `dkms` под текущее ядро, заголовки, три юнита и автозапуск, интерфейс, `ip_forward`, `MASQUERADE`, слушается ли порт, фаервол, сходятся ли пиры в ядре с конфигом — и внутри та же валидация конфига. Ненулевой код возврата, если что-то сломано |
| `amwg validate [файл]` | **перед рестартом** после обновления пакетов; после ручной правки `awg0.conf`; чтобы проверить присланный кем-то конфиг | скармливает конфиг ядру на временном интерфейсе |

Смысл `validate` в том, что иначе узнать «понимает ли новая версия мой конфиг»
можно ровно одним способом: сделать `systemctl restart` и увидеть, что интерфейс
не встал. Вместе со всеми клиентами. Проверка же создаёт временный интерфейс
(`ip link add … type amneziawg`), применяет к нему конфиг и удаляет — живой
`awg0` при этом не трогается вообще. Ловятся обе стадии, на которых конфиг может
не подойти: разбор в `amneziawg-tools` (неизвестный ключ = отказ, так видно, что
из новой версии выкинули параметр) и правила ядра — `S1-S4 ≥ 12` при защите
заголовков, непересечение диапазонов `H1-H4`.

Клиентские конфиги проверять по одному не надо: они генерируются из серверного,
и если серверный принят — приняты и они. Файл аргументом нужен только для чужого
конфига. Модуль при этом должен быть загружен, иначе проверять нечем.

### Обновление ядра

Главная причина, по которой ядерный vpn однажды молча умирает: приехало новое
ядро, dkms-модуль под него не собран, после ребута `awg-quick` падает. Закрыто
двумя вещами:

- ставится **мета-пакет** заголовков (`linux-headers-generic` и аналоги по
  флейвору ядра), а не `linux-headers-$(uname -r)` — заголовки нового ядра
  приезжают вместе с ним, и штатный `/etc/kernel/postinst.d/dkms` пересобирает
  модуль сам;
- `amwg-ensure-module.service` на каждой загрузке добирает несобранное (по **всем**
  ядрам, у которых есть `/lib/modules/*/build`, а не только по текущему) и грузит
  модуль **до** `awg-quick@awg0`. Не вышло — юнит падает с ненулевым кодом, и это
  видно в `systemctl status`, а не «vpn почему-то не подключается».

Третья мелочь оттуда же: у штатного `awg-quick@` нет `Restart=`, и упавший на
загрузке интерфейс так и лежит. Установщик кладёт дроп-ин с `Restart=on-failure`
и `RestartSec=30s` — пять попыток, дальше юнит остаётся в `failed`. Переходящие
причины (модуль досбирался позже, внешнего интерфейса ещё не было и правило
MASQUERADE не применилось) лечатся сами, а настоящая поломка остаётся видимой.
Если упёрся в лимит попыток — `systemctl reset-failed awg-quick@awg0` и стартовать
руками.

Проверить после очередного обновления:

```sh
systemctl status amwg-ensure-module   # что было на загрузке
dkms status | grep amneziawg          # installed под текущее ядро
lsmod | grep -w amneziawg
awg show awg0
```

### Порт

По умолчанию `443/udp`. Важно понимать, чем это является и чем **не** является:
udp на 443 — это территория QUIC, то есть трафик там обычен и сам по себе внимания
не привлекает. Но это не маскировка под сайт: Reality — про TCP:443 и подделку
TLS-хендшейка настоящего сайта, а здесь udp и никакой имитации QUIC нет. У
AmneziaWG за такое отвечают сигнатурные пакеты `I1`-`I5`, и они по умолчанию
выключены — пишутся руками под конкретную маскировку.

То есть порт — слабый сигнал, работу делает обфускация. Практический вывод: 443
хороший дефолт, но если оператор режет QUIC (бывает), на нём станет только хуже —
тогда любой другой: `--port 51820`, `--port 53`. Что именно проходит у твоего
провайдера, проверяется только опытом.

Занят — установщик скажет заранее. Сменить у работающего сервера: поправить `ListenPort` в
`/etc/amnezia/amneziawg/awg0.conf`, правила в `PostUp`/`PostDown`, затем
`systemctl restart awg-quick@awg0`, `amwg server --endpoint host:новый_порт` и
раздать клиентам новые конфиги.

### Фаервол

**Установщик фаервол не трогает.** Открыть машину наружу — решение хозяина
машины, а не установщика vpn, поэтому входящий порт он не разрешает даже там, где
мог бы. Вместо этого он смотрит, что у тебя стоит, и в конце печатает готовую
команду:

| Что найдено | Что напечатает |
|---|---|
| активный `ufw` | `ufw allow 443/udp` |
| `firewalld` | `firewall-cmd --permanent --add-port=443/udp && firewall-cmd --reload` |
| правила `nftables` | `nft add rule inet filter input udp dport 443 accept` (+ как сохранить) |
| свои правила в `INPUT` (`iptables`) | `iptables -I INPUT -p udp --dport 443 -j ACCEPT` (+ `netfilter-persistent save`) |
| ничего из этого | «локального фильтра нет, порт уже доступен» |

Плюс отдельным напоминанием — **security group в облаке**: если сервер в Yandex
Cloud, AWS и подобных, udp-порт открывается ещё и там, иначе клиент до сервера
просто не дойдёт. `amwg check` видит, что порт слушается локально, и умеет
заглянуть в ufw/firewalld/nftables/iptables, но про облачный фильтр не знает
ничего.

Где граница: в `PostUp`/`PostDown` интерфейса остаются `MASQUERADE` и два
`FORWARD ... ACCEPT` — это обвязка самого туннеля, она появляется и исчезает
вместе с интерфейсом, и без неё продукт просто не работает. Ставятся они
**вставкой в начало цепочки** (`-I ... 1`), поэтому политика ufw «forward: DROP»
им не мешает. А вот `INPUT` — это уже про доступ к машине, и туда установщик не
лезет.

### Переезд на другой сервер

Ставь `--endpoint` **доменом**, а не ip: тогда при смене машины достаточно
перекинуть A-запись, и клиентские конфиги останутся рабочими. Цена — имя видно в
dns-запросе перед подключением, ip такого следа не оставляет; выбирать по вкусу.

Адрес меняется в любой момент и ничего не ломает:

```sh
amwg server --endpoint vpn.example.com:443
```

Endpoint вообще не живёт в конфиге интерфейса — он только подставляется в
клиентские конфиги при генерации, поэтому смена мгновенная: ни рестарта, ни
`syncconf`, живые клиенты ничего не замечают. Меняются только конфиги, выданные
**после**; уже розданные надо отдать заново (`amwg show <имя> --qr`). Забыл порт
— утилита подставит его из `ListenPort` интерфейса и скажет об этом; ipv6 пишется
в скобках: `[2001:db8::1]:443`.

Если endpoint был доменом, при переезде не нужно и этого: переставил A-запись —
и всё. Клиент резолвит имя при подъёме туннеля, так что висящее соединение ещё
какое-то время будет стучаться на старый адрес — лечится переподключением, а TTL
записи стоит заранее снизить до минуты.

Сам перенос — через бэкап. `amwg backup` кладёт **один json**: конфиг интерфейса
текстом, всех клиентов с ключами, накопленный трафик и версии, при которых это
работало. Один файл удобно унести `scp`, положить в менеджер паролей и раскатать
одной командой.

```sh
amwg backup                       # на старом: /root/amwg-backup-<хост>-<дата>.json
scp root@old:/root/amwg-backup-*.json .
# на новом — сперва обычная установка, потом:
amwg restore amwg-backup-*.json
```

`restore` кладёт назад конфиг интерфейса вместе с **ключом сервера** — значит
клиентские конфиги остаются рабочими как есть, перевыпускать ничего не надо.
Прежние файлы он не затирает молча, а отодвигает в `.bak-<дата>`, и перед
раскаткой сверяет версии: если на новой машине `amneziawg-tools` или модуль
старше, чем были на старой, он **откажется** — конфиг с параметрами 3.1 на
поколении 3.0 просто не применится (продавить можно `--force`). Сменился адрес —
`amwg restore … --endpoint новый:порт`, и тогда клиентам нужны новые конфиги;
если endpoint был доменом, менять нечего вовсе.

В бэкапе лежат приватные ключи сервера и всех клиентов. Файл создаётся 0600 и
обращаться с ним надо как с ключом.

### Обновиться, ничего не сломав: через новый хост

Самый безопасный способ поднять версию — не трогать работающий сервер вообще:

1. новый хост, обычная установка (встанет текущая версия);
2. `amwg restore backup.json` — приезжают ключ сервера, клиенты и прежняя обфускация;
3. `amwg validate` — ест ли **новая** версия **старый** конфиг. Тут и выясняется
   всё, что могло сломаться, до того как на новый хост пришёл хоть один клиент;
4. проверить лично: у одного клиента временно заменить `Endpoint` на ip нового
   хоста и подключиться;
5. переставить A-запись домена;
6. старый хост подержать сутки-двое (у клиентов кешированный dns) и погасить.

Смена версии бэкапу не мешает — в нём конфиг и ключи, а не бинари. Наоборот, он
тут главный инструмент: на новом хосте оказывается **тот же ключ сервера** и та же
обфускация, поэтому клиентские конфиги остаются рабочими и перевыпускать ничего не
надо — при условии, что `endpoint` был доменом.

Два сервера с одним ключом, работающие одновременно, — это нормально: состояния у
них общего нет, хендшейки независимы, клиент говорит с тем, чей адрес у него в
конфиге.

Если `validate` на новом хосте ругнулся — значит новая версия старый конфиг не
понимает. Старый хост при этом продолжает работать, а на новом надо генерить
конфиг заново (`install.sh --force-config`) и перевыпускать клиентов. Разница в
том, что узнал ты это в спокойной обстановке, а не после `systemctl restart` на
живом сервере.

### Обновление AmneziaWG

Версии зафиксированы `apt-mark hold`, чтобы `apt upgrade` не увёз сервер на
поколение, которое не понимают выданные конфиги. Обновляться осознанно:

```sh
apt-mark unhold amneziawg amneziawg-dkms amneziawg-tools
apt upgrade
awg --version && modinfo -F version amneziawg   # что стало
apt-mark hold amneziawg amneziawg-dkms amneziawg-tools
```

Если поднялось поколение — перевыпустить конфиг (`install.sh --force-config`) и
раздать клиентам новые. До этого момента ничего не трогать: 3.x не обслуживает
клиентов 2.x на том же интерфейсе.

### Снос

```sh
bash install.sh --uninstall --yes          # ключи сложит в /root/awg-backup-*.tar.gz
bash install.sh --uninstall --yes --purge  # заодно снести пакеты
```

### Если что-то не работает

**Модуль не грузится.** `dkms status`, `journalctl -k | tail`, лог сборки в
`/var/lib/dkms/amneziawg/*/$(uname -r)/log/make.log`. Причины, по убыванию частоты:

- **нет заголовков работающего ядра** — `amwg check` говорит прямо: «нет
  `/lib/modules/<версия>/build`». Лечится `apt install linux-headers-$(uname -r)`.
  Если такого пакета для твоего ядра нет вовсе (провайдер загрузил своё), то либо
  переезжай на дистрибутивное ядро (`apt install linux-image-generic` и ребут),
  либо ставь с `--userspace` — там ядро вообще ни при чём;
- **ядро без пакета заголовков или чужое ядро** — тот же симптом на OpenVZ/LXC,
  где модуль не загрузить вообще;
- **загружено старое ядро, а заголовки стоят от нового** (обновились и не
  перезагрузились): после ребута всё встанет само, этим и занимается
  `amwg-ensure-module`;
- **включён Secure Boot** — dkms-модуль надо подписать (`mokutil --import`) или
  выключить SB; установщик про это скажет отдельно.

**Клиент подключился, а сайтов нет.** По порядку: `awg show awg0` (хендшейк
есть?), `sysctl net.ipv4.ip_forward` (=1?), `iptables -t nat -L POSTROUTING -n`
(MASQUERADE на месте? его ставит `PostUp`, значит интерфейс поднимался через
`awg-quick`, а не `ip link`). Если где-то режет MTU — `--client-mtu 1200` и
перевыпустить конфиги.

**Клиент не подключается вообще.** Сверить, что у него конфиг от **этого**
сервера: параметры обфускации обязаны совпадать целиком, а после
`--force-config` они другие.

```sh
journalctl -u awg-quick@awg0 -n 50
systemctl restart awg-quick@awg0   # перечитать конфиг целиком (рвёт сессии)
amwg apply                         # то же самое без разрыва сессий
```

## Установка подробно

| Флаг | По умолчанию | Что делает |
|---|---|---|
| `--endpoint HOST` | внешний ip | адрес (домен или ip) в клиентских конфигах; можно сразу с портом (`host:51820`) — он тогда и станет портом сервера, а конфликт с `--port` считается ошибкой |
| `--port N` | `443` | udp-порт |
| `--iface NAME` | `awg0` | имя интерфейса и конфига |
| `--subnet CIDR` | `10.9.9.0/24` | подсеть туннеля; в /24 влезает 253 клиента |
| `--dns A,B` | `1.1.1.1,1.0.0.1` | DNS для клиентов |
| `--wan IFACE` | из default route | внешний интерфейс для MASQUERADE |
| `--client-mtu N` | `1280` | MTU клиента |
| `--keepalive N` | `25` | `PersistentKeepalive` |
| `--allowed-ips STR` | `0.0.0.0/0, ::/0` | что клиент заворачивает в туннель |
| `--client NAME` | `client1` | первый клиент; `--client ""` — не заводить |
| `--from-source` | нет | собрать tools и модуль из git, минуя PPA |
| `--from-repo` | нет | взять пакеты из `debs/` этого репозитория |
| `--userspace` | нет | вместо ядерного модуля — `amneziawg-go` (см. ниже) |
| `--single-headers` | нет | `H1-H4` одиночными числами вместо диапазонов |
| `--no-timings` | нет | не писать тайминги 3.0 |
| `--no-hold` | нет | не фиксировать версии пакетов |
| `--no-stats-timer` | нет | не ставить таймер учёта трафика |
| `--force-config` | нет | перегенерить конфиг интерфейса |
| `--no-ask` | нет | не спрашивать адрес даже в живой консоли |
| `--amwg PATH\|URL` | рядом со скриптом или из `AWG_REPO_RAW` | откуда взять `amwg.py` |
| `--uninstall --yes` | — | снести всё, сложив ключи в `/root` |

Любой флаг задаётся и переменной окружения: `AWG_ENDPOINT`, `AWG_PORT`,
`AWG_IFACE`, `AWG_SUBNET`, `AWG_DNS`, `AWG_WAN`, `AWG_CLIENT_MTU`,
`AWG_KEEPALIVE`, `AWG_ALLOWED_IPS`, `AWG_FIRST_CLIENT`, `AWG_VERSION`,
`AWG_REPO_RAW`.

> `--force-config` перевыпускает ключ сервера и всю обфускацию: **всем клиентам
> понадобятся новые конфиги**. Старый файл остаётся рядом как `.bak-<дата>`.

Из чекаута (тогда `amwg.py` берётся из соседнего файла, а не из сети):

```sh
bash install.sh --endpoint vpn.example.com --port 443
```

`AWG_REPO_RAW` нужен ровно за одним: дотянуть `amwg.py`, когда установщик
прилетел через пайп и рядом с ним ничего нет.

### Что делает установщик

1. Ставит базовое: `curl`, `gnupg`, `iproute2`, `iptables`, `qrencode`, `python3`.
2. Подключает **официальный PPA Amnezia** — ключ тянется с keyserver и сверяется
   по полному отпечатку `75C9DD72C799870E310542E24166F2C257290828`.
3. Ставит `amneziawg` (метапакет → `amneziawg-tools` + `amneziawg-dkms`) и
   мета-пакет заголовков ядра.
4. **Проверяет версию**: `awg --version` и `modinfo -F version amneziawg` должны
   дать не ниже 3.1. Не дали — собирает tools и модуль из исходников; и после
   этого не дали — падает, а не делает вид, что всё хорошо.
5. Фиксирует версии пакетов (`apt-mark hold`).
6. sysctl: `ip_forward`, форвардинг v6, `bbr` + `fq`, udp-буферы.
7. Генерирует конфиг со **случайными** параметрами обфускации, ключом сервера и
   правилами NAT в `PostUp`/`PostDown`.
8. Кладёт `amwg`, включает `awg-quick@awg0` (с дроп-ином на переподъём при сбое),
   `amwg-ensure-module.service` и таймер учёта трафика, заводит первого клиента.

Чего он **не** делает: не сносит `unattended-upgrades`, `snapd` и `cloud-init`,
не требует перезагрузок, не лезет в ssh, не ставит fail2ban и **не управляет
фаерволом** — только подсказывает командой, чем открыть порт (см.
[Фаервол](#фаервол)).

### Куда что ложится

| Путь | Что |
|---|---|
| `/etc/amnezia/amneziawg/awg0.conf` | конфиг интерфейса: `[Interface]` от установщика, `[Peer]` от `amwg` |
| `/etc/amnezia/amneziawg/amwg/state.json` | клиенты: ключи, ip, вкл/выкл, заметки (0600) |
| `/etc/amnezia/amneziawg/amwg/traffic.json` | накопленный трафик и последний хендшейк |
| `/usr/local/bin/amwg` | утилита управления |
| `/usr/local/sbin/amwg-ensure-module` | сборка и загрузка модуля |
| `/etc/systemd/system/amwg-ensure-module.service` | он же на каждой загрузке |
| `/etc/systemd/system/amwg-poll.{service,timer}` | учёт трафика раз в 5 минут |
| `/etc/systemd/system/awg-quick@awg0.service.d/10-amwg.conf` | переподъём интерфейса при сбое |
| `/etc/sysctl.d/99-amneziawg.conf` | форвардинг, bbr, буферы |
| `/etc/apt/sources.list.d/amnezia-ppa.list` | репозиторий Amnezia |

## Как это устроено

### Почему не панель и не докер

- **Поколение 3, а не 1.5.** Версии AmneziaWG между собой несовместимы, и все
  популярные панели (`wg-easy` с `EXPERIMENTAL_AWG`, форки `amnezia-wg-easy`)
  умеют только 1.5: `Jc/Jmin/Jmax`, `S1-S4`, `H1-H4`, `I1-I5`. Ни защиты
  заголовков, ни паддинга контента, ни таймингов там нет — а это и есть ответ на
  то, чем ТСПУ занялся летом 2026: анализ поведения соединения целиком, а не
  сигнатуры отдельного пакета.
- **Ядерный модуль, а не `amneziawg-go`** (но `--userspace` есть). Официальный клиент по ssh
  разворачивает контейнер с userspace-реализацией на go. Контейнер там ради
  удобства GUI: на голом железе ядерный модуль быстрее и проще в эксплуатации.
- **Своя утилита, а не панель.** `amneziawg-tools` — форк `wireguard-tools`, вся
  специфика в параметрах конфига. Управление клиентами — это генерация конфига по
  шаблону, `awg syncconf` и учёт в json.

### Параметры обфускации

Всё, кроме `Jc/Jmin/Jmax`, **обязано совпадать** у сервера и клиента — требование
самой Amnezia. `amwg` копирует параметры из серверного конфига в клиентский сам,
сверять руками нечего.

| Параметр | Значение | Зачем |
|---|---|---|
| `Jc`, `Jmin`, `Jmax` | случайные 4-12, 8-24, 64-320 | мусорные пакеты перед handshake; **у каждого клиента свои** |
| `S1`-`S4` | случайные 15-150 | мусор внутри служебных пакетов; при защите заголовков обязаны быть ≥ 12, и `S1 + 56 ≠ S2` |
| `H1`-`H4` | случайные непересекающиеся диапазоны | типы сообщений; диапазон (фича 3.0) заставляет заголовок гулять от пакета к пакету |
| `HeaderProtectionKey` | `awg genpsk` | ChaCha20 поверх заголовков WireGuard |
| `ContentPaddingAddition` | `8-32`–`48-96` | случайный паддинг полезной нагрузки |
| тайминги | диапазоны вокруг дефолтов ядра (120/5/180/10/18) | чтобы тайминги соединения не были опознаваемой константой |
| `RandomTrailers` | `on` | случайные хвосты пакетов (3.1) |
| `DisableCookies` | `on` | отключение Cookie Reply (3.1) |
| `I1`-`I5` | выключены | сигнатурные пакеты пишутся руками под конкретную маскировку |

`DisableCookies = on` — сознательный размен: cookie reply это защита от DoS с
подделкой адреса. Персональному серверу она нужна меньше, чем невидимость, но
если сервер начнут долбить — убирать этот параметр первым (и у клиентов тоже).

IPv6 внутрь туннеля не заворачивается: у интерфейса нет v6-адреса, а `::/0` в
`AllowedIPs` уводит v6-трафик клиента в туннель, где он гасится. Реальный
v6-адрес наружу не течёт, и это ровно то, что нужно.

### Откуда берутся пакеты и почему они лежат в репозитории

По умолчанию — официальный PPA Amnezia. Но у него есть неприятное свойство:
**он роллинговый и старые сборки из него исчезают**. Проверял руками: версия
tools 3.0, вытеснённая 13 августа, уже отдаёт `404`, хотя текущая качается
нормально. Launchpad помнит о ней в api, файла нет. Значит `apt install
amneziawg=<точная версия>` не сработает даже через месяц, не то что через год, и
«поставить ровно ту же версию, что стоит сейчас» через PPA невозможно в принципе.

Поэтому текущие сборки лежат прямо здесь, в `debs/` — всё вместе около мегабайта:

| Файл | Размер | Зачем |
|---|---|---|
| `debs/noble/amneziawg-tools_…_amd64.deb` и `_arm64.deb` | ~106-111 КБ | `awg`, `awg-quick` |
| `debs/noble/amneziawg-dkms_…_all.deb` | ~285 КБ | исходники модуля для dkms |
| `debs/noble/amneziawg_…_all.deb` | 6 КБ | метапакет |
| `debs/jammy/…` | то же | для debian и ubuntu 22.04 |
| `debs/<серия>/SHA256SUMS` | — | суммы, установщик их сверяет |

Разложено по сериям: `debs/noble/` и `debs/jammy/`, в каждой свой `SHA256SUMS`.
Из комплекта установщик берёт файлы своей архитектуры и arch-independent.

Ставится это флагом, а не автоматически:

```sh
bash install.sh --from-repo --endpoint vpn.example.com
```

Автоподстановки тут нет намеренно: тихо поставить замороженные пакеты вместо
свежих — плохая идея, такое должно быть решением. Если PPA не отдал нужную версию,
установщик сперва пробует собрать из исходников и **подсказывает** про `--from-repo`.

Зависимости у пакетов копеечные (`dkms`, `perl`, `libc6`), они берутся из
штатного репозитория дистрибутива, так что офлайн-путь работает и без PPA.
Обновить запас — скачать свежие `.deb` из PPA и переписать `SHA256SUMS`:

```sh
cd debs/noble && sha256sum ./*.deb | sed 's|\./||' > SHA256SUMS
```

Заметь: сборка под `noble` требует `libc6 >= 2.38`, поэтому на debian 12/13 и
ubuntu 22.04 нужен именно `~ubuntu22.04.1`-комплект — установщик это учитывает.

### Пакеты, серии и ядра

Сверено с launchpad api по коммиту в версии пакета:

| Что | Где есть 3.1 |
|---|---|
| `amneziawg-tools` (коммит `ee0f0a9`) | **только `jammy` и `noble`**; `focal`, `bionic`, `xenial` застряли на 3.0 (`9f70177`) |
| `amneziawg-dkms` (коммит `3c38e16`) | во всех LTS-сериях; `oracular`, `plucky` старые |

Отсюда логика выбора серии: убунты — своя серия, если она в списке, иначе `noble`;
debian и остальные apt-дистрибутивы — `jammy` (его glibc 2.35 старше дебиановской,
бинарь заводится и на 12, и на 13 — проверено). На всём, где версия оказалась
ниже 3.1, установщик молча уходит на сборку из исходников — потому что tools 3.0
не знают ключей `RandomTrailers` и `DisableCookies`, и конфиг с ними не применится.

RHEL/Fedora не поддержаны: там свой путь через
`dnf copr enable amneziavpn/amneziawg`, а дальше конфиг и `amwg` — руками.

Про ядро: сборка 3.x требует ядра не старше приличного (около 6.x), на 6.1 модуль
собирается, но обкатан слабо. Ubuntu 24.04+ снимает вопрос.

### Три поправки к тому, что пишут в интернете

- **`HeaderProtectionKey` — не hex.** В `amneziawg-tools` он разбирается тем же
  `parse_key`, что и обычные ключи: 32 байта в base64, то есть то, что выдаёт
  `awg genpsk`.
- **Пакет модуля называется `amneziawg-dkms`.** `amneziawg-linux-kmod` — это имя
  исходного пакета на Launchpad, ставить надо метапакет `amneziawg`.
- **`modinfo -F version amneziawg` показывает `1.0.0` — и это НЕ поколение
  протокола.** В `Makefile` модуля жёстко зашито `WIREGUARD_VERSION = 1.0.0`, и
  оно перебивает `version.h`, где лежит настоящее `3.1.20260812`. Так что версия
  модуля вообще ни о чём не говорит: и 3.1, и что угодно другое отрапортуют
  одинаково. Проверять поколение можно только функционально — применить к
  временному интерфейсу конфиг с параметрами 3.1 и посмотреть, примет ли ядро.
  Именно так делают `install.sh` при установке и `amwg validate`. Проверено на
  собранном и загруженном модуле 3.1.

## Чего здесь нет

- Веб-панели и http-раздачи конфигов: конфиг с ключом — секрет, его отдают qr с
  экрана или файлом по scp, а не ссылкой.
- Сроков жизни клиентов и квот по трафику: считать байты `amwg` умеет, резать по
  лимиту — нет.
- Настройки самого хоста (ssh, fail2ban, автообновления) — не его дело.
